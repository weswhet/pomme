## Stop path (#1's likely cause) — `abd56a4`

`stop` sent the framework's stop request and, 30 seconds later, cut the VM's
power while still printing `OK stopped`. VZ's request behaves like a power
button that macOS can take a minute to act on, so healthy guests were being
power-cut: `Docs/CreationPerformance-2026-09-13.md` had measured 31 seconds
for a stop that ended in a force and named the remedy for the public command.

`stop` now asks the guest to run `shutdown -h now` when the VM is running in
normal boot with the agent connected, as provisioning and the Recovery paths
already did. A paused VM is resumed first, since a paused guest can neither be
asked to shut down nor act on the framework request; `--force` skips that. A
guest that was asked to shut down gets 120 seconds, and every other stop keeps
the 30 second window it had, so no path waits longer than before without a
reason. The reply carries `stopMethod` and the output names a power-off.

Live: a running guest stops in 6.7 s as `guest-stopped`, a paused one in
2.4 s, `--force` in 0.3 s, and a Recovery stop forces at 30.5 s and says so.
The snapshot-restore sequence that broke a VM on 2026-09-17 now ends with a
working guest.

This removes the mechanism most likely behind #1, which stays open: the
failure was never reproducible on demand. The next occurrence will be
self-documenting, because whichever stop precedes it will have reported
`forced`.

## 5. `restart` ends on its boot line — `475ee8f`

`restart` replaced the boot payload's steps with its own and re-formatted it;
`formatBoot` returns the last step carrying a `response`, which since
`282fb77` was the stop's. The line now comes from the boot result. A restart
whose guest had to be powered off keeps that line above the boot line.

The same commit made only a stop that asked for a guest shutdown wait the
long window, after the Recovery-bound restart was measured waiting it out for
nothing. The lifecycle request carries `guestShutdownRequested`, an additive
field an older helper ignores.

Live: `restart` prints `OK boot mode=normal` in 16.2 s; `restart --mode
recovery` prints the forced-stop line then `OK boot mode=recovery` in 31.9 s,
not the 120 s the previous build would have taken.

## 4. `status` no longer claims a job count — `90034ca`

`status` printed `jobs=0` for every VM, including one with a running detached
job, and its JSON had no `jobs` field at all. The count read a key the helper
never sets; background jobs live in the guest agent's table, which `jobs list`
reads. The line drops the count and the offline payload drops the empty key.
Populating it would put a guest round trip in every status call, including the
polling loops that `start`, `restart`, and the security workflows run.

Live: with a detached `sleep 120` running, `status` reads `VM running
boot=normal helper=true`, `jobs list` shows the job, and the JSON has no
`jobs` key.

## 3. A timed-out foreground command says what happened — `407b611`

The timeout said the guest job was still running and to find it with `jobs
list`. Both foreground paths SIGTERM the process before giving up, and `jobs
list` only holds detached jobs, so the process was usually gone and never
listed. The message is now built from what the request recorded: a signalled
process reads "the guest process was signalled to stop" and names `--detach`
for work that should outlive the request, while one that could not be
signalled admits it may still be running.

Live: `exec --timeout 1 -- /bin/sleep 30` exits 124 with the new message, and
`ps` in the guest shows no `sleep 30` left.

## 2. A usable guest after a security workflow — `463c6bf`

A guest command issued after `sip` or `amfi` returned failed for minutes with
`PommeAgent is not connected on port 505051`. A workflow whose final state is
a normal boot called `startRuntimeInBackground` directly and returned as soon
as the helper was up, while `pomme start` and the provisioning path both wait
for the agent. The security path now waits the same way, non-fatally: the
security result is authoritative, so an agent that does not connect in time is
logged rather than failing a workflow that already succeeded.

The failure text also read like a port misconfiguration. It now says a guest
that is still booting connects on its own and that `status` reports when it
does, and a connection that is mid-authentication is reported as connecting
and worth retrying.

Live: `sip status` took 3 m 14 s (about 13 s longer than before) and the
`exec` immediately after it succeeded in 0.37 s, where that window used to
fail for two to four minutes. In Recovery, where there is no normal agent, a
guest command reports the new wording.

Not fixed: an exchange that times out while the agent reports connected, seen
once right after a create. That is the guest being slow rather than absent,
and retrying a mutating guest operation is deliberately not done. #2 stays
open for that half.
